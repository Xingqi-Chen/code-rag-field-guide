# Microsoft GraphRAG 适合做开发助手的代码索引吗？

把代码仓库想成图书馆：关键词搜索查原文，向量检索按意思找段落，Microsoft GraphRAG 则先制作“事物卡片”和关系导读。导读可能带来线索；真正改代码，还要找到**具体哪一页、哪个版本、哪些调用者和测试**。

**[阅读中文主报告](docs/report.md)** · [实验方法与复算](research/pilot/full-run.md) · [官方源码与证据](research/README.md)

研究固定 **Microsoft GraphRAG v3.3.0**，截止 **2026-10-12**，聚焦四项开发任务。默认文档实体图与程序的符号／调用图是两种东西，不能因为都有“图”，就认定能解决相同问题。

**实验当前暂停，等待单次重试授权；没有自动重试。** 已冻结 Requests 的41个文件、114块、20个检索问题和2个功能任务；原版59项离线回归通过。正式微软索引已真实启动，第159次生成请求在60秒处超时停止，158条成功结果已缓存。同一块可能触发多次请求，因此成功请求数不等于已完成块数或实验完成比例。尚无完整索引、检索分数或功能补丁成绩；中断不能解释为GraphRAG效果差。见[脱敏执行记录](research/pilot/results/execution-interrupted.json)。后续比较BM25、同embedding的hybrid、Microsoft Basic与Local，统一4000/12000-token最终上下文，问题与评分规则不因结果改变。

| 你想完成的任务 | 已核实的能力边界 | 本次效果证据 |
| --- | --- | --- |
| 精确找函数／符号 | 默认流程没有与语言解析绑定的唯一符号身份和源码行号保证 | 待检索评测 |

**当前工程判断：把它作为待验证的补充检索路线，不能当作可靠符号、调用及影响分析工具的直接替代。** 文档和代码说明分散、自然语言需求与命名不一致时，值得检验它能否补到基线漏掉的证据；要求完整调用者集合、稳定源码位置或修改／删除同步时，需要额外的程序工具和版本管理。这是源码支持的判断，尚不是本轮测得的效果胜负。

[四张图](docs/figures/README.md)及[小店代码](docs/examples/shop/README.md)是原创教学示例，**不是微软实验输出**。旧自制代码图实验保留在[正常Git历史](research/legacy.md)，不算新版微软效果证据。[接口探测历史](research/pilot/probe-result.md)与正式评测分开记账。
